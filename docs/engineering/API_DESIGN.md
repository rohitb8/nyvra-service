# API_DESIGN.md — nyvra-backend

Conventions for the public REST API, plus the v1 endpoint map for the first four areas
(accounts, income, expenses, health score). The machine-readable contract is
`src/main/resources/openapi/nyvra-api-v1.yaml`; this doc explains the *why* and the rules every
endpoint follows, so new endpoints don't re-decide them.

Status: **v0.1 draft, 2026-10-06** — under review, not frozen. `TODO.md` Phase 3.1. The spec is
written contract-first; once controllers exist (Phase 3.3), springdoc's export must match it and
the CI drift check (Phase 3.5) keeps the two in step.

Reads with: `docs/product/DOMAIN_MODEL.md` (resources = aggregates), `database/schema.dbml`
(fields), `docs/product/HEALTH_SCORE_SPEC.md` (score shape), `docs/engineering/CODE_STYLE.md`
§4–5 (DTOs, controllers). Frontend side: `nyvra-ui` → `docs/engineering/STATE_AND_DATA_FETCHING.md`.

## 1. Resources & URLs

- Base path `/api/v1`. Every endpoint requires a Keycloak bearer token (`ROLE_USER`); there are no
  public endpoints besides actuator/swagger.
- **Plural kebab-case nouns**: `/accounts`, `/income/sources`, `/categorisation-rules`.
  Module-scoped resources share a prefix when the noun alone is ambiguous (`/income/sources`,
  `/income/entries`) — otherwise top level.
- **Nest only for true containment**, one level deep: `/accounts/{accountId}/transactions`. The
  same items are also reachable flat (`/transactions?accountId=`) for cross-account views.
- **No user id in any URL.** The token's `sub` scopes every call (`/users/me` is the only "me"
  path). A resource that exists but belongs to another user returns **404, never 403**, so ids
  can't be probed.
- **State changes that aren't field edits are sub-resource actions**: `POST /accounts/{id}/close`,
  `POST /expenses/{id}/split`. No verbs anywhere else.
- **Read-only derived views** (computed by the backend, never by the client) live under the area
  they summarise: `/spending/habits`, `/income/summary`, `/health-score`.
- IDs are UUIDs (v7, generated by the app) and are opaque to clients.

## 2. Methods & status codes

| Method | Use | Success |
|---|---|---|
| `GET` | read one / list | `200` |
| `POST` (collection) | create | `201` + `Location` header + body |
| `POST` (action) | close, split, … | `200` + updated resource |
| `PATCH` | partial update — **omitted field = unchanged**; explicit `null` clears an optional field | `200` + updated resource |
| `DELETE` | soft delete (`deleted_at`) where the aggregate supports it | `204` |

No `PUT` in v1: every editable resource has system-owned fields (source, balances, computed
values), so a full replace would always be partial anyway.

Records that arrived via Account Aggregator are **read-only for their source data** (amount,
date, balance, narration). Users can still edit *their* annotations on them (label, category,
necessity). Trying to edit AA source data → `409 SOURCE_READ_ONLY`.

## 3. Pagination, sorting, filtering

Two schemes, chosen per resource by volume:

| Scheme | Params | Envelope | Used for |
|---|---|---|---|
| **Page** | `?page=0&size=20` (0-based, `size` ≤ 100, default 20) | `{ content, page, size, totalElements, totalPages }` | bounded lists: accounts, income sources, income entries, categorisation rules |
| **Cursor** | `?cursor=…&limit=50` (`limit` ≤ 200, default 50) | `{ content, nextCursor, limit }` — `nextCursor` absent on the last page | high-volume, partitioned feeds: transactions, expenses |

Why mixed: `transaction` and `expense` are range-partitioned and grow without bound; `COUNT(*)`
for `totalElements` and deep `OFFSET`s get expensive, and an infinite-scroll feed doesn't need
them. Cursors are keyset-based on `(date DESC, id DESC)`, opaque base64 strings — clients pass
them back verbatim and never build or parse them. A cursor is bound to the filters it was issued
with; changing a filter means starting without a cursor.

- **Sorting** (page lists only): `?sort=field,asc|desc`, repeatable. Each endpoint documents its
  allowed sort fields; anything else → `400`. Cursor feeds have a fixed order (newest first).
- **Filtering**: plain query params per endpoint (`accountId`, `from`, `to`, `categoryId`, …).
  Date ranges are inclusive `from`/`to` (`yyyy-MM-dd`); a month is `month=yyyy-MM`. `from > to`
  → `400`.
- Use `size`, not `pageSize` (Spring's `Pageable` default). The frontend's draft §6 says
  `pageSize`; it adopts this name when it generates the client.

## 4. JSON conventions

- **camelCase** fields. **Nulls are omitted** (`JacksonConfig` → `NON_NULL`): an absent field
  means "no value", and generated clients mark such fields optional.
- **Money** is an object, never a bare number:
  ```json
  { "amount": "125000.00", "currency": "INR" }
  ```
  `amount` is a **decimal string** — scale 2 for amounts, up to scale 6 for prices/NAV/quantities
  (`docs/engineering/DATABASE_DESIGN.md`). Strings avoid IEEE-754 rounding in transit; the client
  only parses them to format for display, never to do arithmetic. Request bodies use the same
  shape; amounts with more decimals than the field's scale → `400`. `currency` is ISO-4217,
  `INR` in v1 (anything else → `422 UNSUPPORTED_CURRENCY` until multi-currency exists).
- **Percentages** are JSON numbers in **percent points**, one decimal, `0`–`100`
  (`42.5` means 42.5%) — exactly what the UI's `percent1` pipe takes. **Scores** are numbers,
  one decimal, `0`–`100`. **Ratios** (where a spec defines one, e.g. confidence) are numbers with
  their spec's precision. None of these are money, so floats are fine.
- **Dates**: accounting dates (`LocalDate`) → `"2026-10-06"`; instants → UTC
  `"2026-10-06T04:30:00Z"`. The server never applies a time zone; the client renders in
  `Asia/Kolkata`. Months → `"2026-10"`.
- **Enums** are `UPPER_SNAKE` strings matching `schema.dbml`. Clients must tolerate unknown enum
  values (show a generic label) — adding a value is not a breaking change (§8).
- **Provenance on every user-visible number** (`DOMAIN_MODEL.md` cross-cutting rules): anything
  that can go stale carries `source` (`AA` / `MANUAL` / `DERIVED`) and an as-of timestamp
  (`balanceAsOf`, `asOf`, `computedAt`). The UI's freshness labels read these.
- **No sensitive values beyond what the user already sees**: account numbers are masked
  (`XXXX1234`), cards are `last4` + network only, never a PAN/CVV/expiry. Encrypted columns
  (`narration`, `counterparty`, `masked_number`) are decrypted server-side for the owner only.

## 5. Errors

Every non-2xx body is `ApiError` (`common/exception/ApiError.java`):

```json
{
  "timestamp": "2026-10-06T04:30:00Z",
  "status": 422,
  "error": "Unprocessable Entity",
  "code": "INCOME_PERIOD_OVERLAP",
  "message": "This period overlaps an existing entry for the same income source.",
  "path": "/api/v1/income/entries",
  "details": ["periodStart: overlaps entry for 2026-09-01..2026-09-30"],
  "traceId": "8f0c2b6e1a4d4c3e"
}
```

**Proposed addition: `code`** — a stable machine-readable string (the frontend maps it to
microcopy; `message` stays a safe English fallback). It's additive to the existing record, so
`GET /users/me` is unaffected. Generic codes per status, plus domain codes:

| Status | Generic `code` | When | Domain codes (v1) |
|---|---|---|---|
| 400 | `BAD_REQUEST` / `VALIDATION_FAILED` | malformed JSON, bad param, Bean Validation failure (`details` = `field: message`) | — |
| 401 | `UNAUTHENTICATED` | missing/expired/invalid token | — |
| 403 | `FORBIDDEN` | role missing (not used for ownership — see §1) | — |
| 404 | `NOT_FOUND` | unknown id or another user's resource | — |
| 409 | `CONFLICT` | state conflicts | `SOURCE_READ_ONLY`, `ACCOUNT_CLOSED`, `IDEMPOTENCY_KEY_REUSED`, `CATEGORY_IN_USE`, `ALREADY_SPLIT` |
| 422 | `UNPROCESSABLE` | well-formed but violates a domain invariant | `INCOME_PERIOD_OVERLAP`, `NET_EXCEEDS_GROSS`, `EXPECTED_AMOUNT_REQUIRED`, `SPLIT_SUM_MISMATCH`, `UNSUPPORTED_CURRENCY`, `SYSTEM_CATEGORY_IMMUTABLE` |
| 413 | `PAYLOAD_TOO_LARGE` | payslip over the size limit | — |
| 415 | `UNSUPPORTED_MEDIA_TYPE` | payslip not PDF/PNG/JPEG | — |
| 429 | `RATE_LIMITED` | per-user rate limit (Phase 7); `Retry-After` header set | — |
| 500 | `INTERNAL_ERROR` | anything unhandled — `message` is generic, never the exception text | — |

400 vs 422: **400** = the request can't be understood or fails field-level validation on its own;
**422** = each field is valid but together they break a business rule.

## 6. Idempotency

- Every **creating** `POST` (collection creates, `split`, payslip upload) accepts an optional
  `Idempotency-Key` header (UUID, client-generated per user action, reused on retry).
- The server stores `(userId, key) → (request hash, status, response body)` in Redis with a
  **24 h TTL**. A repeat with the same key and same body replays the stored response (same status,
  plus `Idempotent-Replayed: true`); same key, different body → `409 IDEMPOTENCY_KEY_REUSED`.
- Optional, not required, in v1: the SPA sends it on every create; the OpenAPI marks it optional so
  scripts and Swagger UI still work without it.
- `PATCH`/`DELETE`/action endpoints that are naturally idempotent (`close`, delete) don't need it.

## 7. Caching & concurrency

- List/detail responses send `Cache-Control: private, no-store` (financial data must not land in
  shared caches). The client's TanStack Query cache is the only cache.
- No optimistic-locking headers (`ETag`/`If-Match`) in v1: data is single-user, and AA ingestion
  never edits the user-owned annotation fields that `PATCH` touches. Revisit if multi-device
  editing conflicts show up.

## 8. Versioning & deprecation

- **Additive changes stay in v1**: new endpoints, new optional request fields, new response
  fields, new enum values. Clients must ignore unknown fields and tolerate unknown enum values.
- **Breaking changes go to `/api/v2`** (removing/renaming a field, changing a type or meaning,
  making an optional request field required, tightening validation). v1 is never mutated in place.
- A deprecated endpoint/field gets `Deprecation: true` and `Sunset: <http-date>` headers and
  `deprecated: true` in the spec, with at least one frontend release in between before removal.
- The spec's `info.version` follows semver within v1 (`1.0.0`, `1.1.0` for additions). Tag
  `api-v1.0` when the frontend first generates against it.

## 9. v1 endpoint map (this draft)

### Accounts (`accounts` module)

| Method | Path | What | Notes |
|---|---|---|---|
| GET | `/accounts` | list accounts | page; filters `type`, `status`, `source`; sort `label`, `type`, `balanceAsOf`, `currentBalance` |
| POST | `/accounts` | create a **manual** account | `source` is always `MANUAL`; AA accounts appear via ingestion |
| GET | `/accounts/{accountId}` | one account | includes `card` for `CREDIT_CARD` |
| PATCH | `/accounts/{accountId}` | edit label/institution (any); balance + card limit (manual only) | balance edit on AA account → `409 SOURCE_READ_ONLY` |
| POST | `/accounts/{accountId}/close` | mark `CLOSED` | keeps history; excluded from net worth from then on |
| DELETE | `/accounts/{accountId}` | soft-delete a **manual** account | AA accounts are closed, not deleted (consent revocation is the `aggregator` API, later) |
| GET | `/accounts/{accountId}/transactions` | that account's ledger | cursor; filters `from`, `to`, `direction` |
| GET | `/transactions` | ledger across all accounts | cursor; filters `accountId` (repeatable), `from`, `to`, `direction` |
| GET | `/transactions/{transactionId}` | one transaction | read-only — transactions are immutable |

### Income (`income` module)

| Method | Path | What | Notes |
|---|---|---|---|
| GET | `/income/sources` | list sources | page; filters `type`, `active` |
| POST | `/income/sources` | create | `expectedAmount` required unless `cadence = IRREGULAR` (`422 EXPECTED_AMOUNT_REQUIRED`) |
| GET / PATCH / DELETE | `/income/sources/{sourceId}` | one source | DELETE soft-deactivates (`active=false`) if it has entries, so history stays explainable |
| GET | `/income/entries` | list entries | page; filters `sourceId`, `type`, `from`, `to` (on `receivedOn`); sort `receivedOn`, `periodStart` |
| POST | `/income/entries` | create a manual entry | `net ≤ gross` (`422 NET_EXCEEDS_GROSS`); no period overlap per source (`422 INCOME_PERIOD_OVERLAP`) |
| GET / PATCH / DELETE | `/income/entries/{entryId}` | one entry | `AA_DETECTED` entries: amounts read-only |
| POST | `/income/entries/{entryId}/payslip` | upload a payslip (multipart, `file`) | PDF/PNG/JPEG ≤ 5 MB; stored in object storage; parse is async → `parseStatus` |
| GET | `/income/entries/{entryId}/payslip` | payslip metadata + parsed fields | file bytes are never served back in v1 |
| GET | `/income/summary` | rolling monthly averages + by-type totals | `?window=3\|6\|12` months (default 3); server-computed, for the Income screen header |

### Expenses (`expense` module)

| Method | Path | What | Notes |
|---|---|---|---|
| GET | `/expenses` | expense feed | cursor; filters `month` **or** `from`/`to`, `categoryId`, `necessity`, `origin`, `q` (merchant contains) |
| POST | `/expenses` | create a manual expense | `origin = MANUAL` |
| GET | `/expenses/{expenseId}` | one expense | includes `splits` when split |
| PATCH | `/expenses/{expenseId}` | recategorise / change necessity / merchant / `excludedFromHabits`; amount + date for `MANUAL` only | AA amount/date edit → `409 SOURCE_READ_ONLY` |
| DELETE | `/expenses/{expenseId}` | soft-delete a **manual** expense | AA-derived expenses are excluded via `excludedFromHabits`, not deleted |
| POST | `/expenses/{expenseId}/split` | split into ≥ 2 parts | parts must sum to the parent exactly (`422 SPLIT_SUM_MISMATCH`); re-splitting → `409 ALREADY_SPLIT` (unsplit first) |
| DELETE | `/expenses/{expenseId}/split` | undo a split | children removed, parent restored |
| GET | `/categories` | category tree (system + user's custom) | unpaged tree, small and cacheable |
| POST | `/categories` | add a custom child category | `parentId` required — users add children only |
| PATCH / DELETE | `/categories/{categoryId}` | rename/delete a custom category | system → `422 SYSTEM_CATEGORY_IMMUTABLE`; delete in use → `409 CATEGORY_IN_USE` |
| GET | `/categorisation-rules` | the user's rules | page; sort `priority` |
| POST | `/categorisation-rules` | create | `?applyToExisting=true` re-categorises matching uncategorised/auto-categorised history |
| GET / PATCH / DELETE | `/categorisation-rules/{ruleId}` | one rule | system rules aren't exposed |
| GET | `/spending/habits` | the month's breakdown | `?month=yyyy-MM` (default current); totals, essential vs discretionary %, per-category amount + % |

### Health score (`analytics` module)

| Method | Path | What | Notes |
|---|---|---|---|
| GET | `/health-score` | latest score | always `200`: with < 3 evaluated sub-scores (or none computed yet) → `band: INSUFFICIENT_DATA`, no `overall`, plus `missingData` checklist |
| GET | `/health-score/history` | score trend | `?from=&to=&granularity=DAY\|WEEK\|MONTH` (default last 180 days, `WEEK`); one point per bucket = the last score in it |

The score response mirrors `HEALTH_SCORE_SPEC.md` §1, with three deliberate differences:
1. `confidenceLevel` (`LOW`/`MEDIUM`/`HIGH`) is returned alongside `confidence`, so the UI never
   applies the `0.5 / 0.8` thresholds itself (frontend rule: no business thresholds in the UI).
2. A hard cap is reported explicitly as `cap: { value, reason }` *and* its reason code is appended
   to `topDrivers`, per the spec.
3. `inputsHash` is internal (skip-recompute bookkeeping) and **not** exposed. `rulesetVersion` and
   `scoreSpecVersion` are, so a historical score stays explainable.

### Out of this draft (later passes)

Portfolio, net worth, dashboard summary, trends, insights, goals, aggregator/consents, and the
rest of `/users/me` (profile/preferences/consents/export/deletion). `GET /users/me` is in the spec
because it already ships.

## 10. Open questions for review

1. **Custom categories need an owner** — *resolved in V4*: `category` has a nullable `user_id`
   (`null` = system category; names unique per user and parent — `database/decisions.md` §7).
   The API needs no change:
   `GET /categories` returns system categories plus the caller's own, and custom ones are
   `system: false`.
2. **"By cadence" spending view.** The frontend IA shows Spending *by cadence* (monthly fixed /
   monthly variable / periodic) and an upcoming-periodic-expenses timeline. Nothing in the schema
   or `FINANCIAL_RULES.md` defines cadence on an expense. Left out of this draft; it needs a
   domain decision first (recurring-expense detection?).
3. **Income type "Refunds".** The frontend IA lists Refunds as an income type; `income_type` has no
   `REFUND`. Either add the enum value (additive) or map refunds to `OTHER`/negative expenses.
   Draft assumes **refunds are negative expenses, not income**, so they don't inflate savings rate.
4. **Money as string vs the UI pipes.** `inrCurrency` takes a `number`. The UI would do
   `Number(amount)` purely for formatting — safe for any realistic rupee value, but worth a
   one-line exception in the UI's "no math" rule. Alternative: pipes accept `string`.
5. **`ApiError.code`** — confirm the additive field (§5).
6. **Manual transactions.** `transaction.source` allows `MANUAL`, but this draft has no
   `POST /transactions`: manual cash spending is entered as a manual *expense*, and manual
   accounts only carry a balance. Confirm that's enough for v1.
